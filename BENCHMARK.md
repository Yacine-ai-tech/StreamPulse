# Benchmark Results

This document summarizes StreamPulse's measured classifier accuracy, throughput, and webhook
security. Full methodology and per-run detail are in the `eval/` directory.

---

## 1. Domain Classifier Accuracy

Measured on a curated, balanced set deliberately paraphrased to avoid literal domain
keywords, designed to stress-test the vector-embedding and LLM tiers rather than keyword
matching. Full detail: [`eval/CLASSIFIER_BENCHMARK.md`](eval/CLASSIFIER_BENCHMARK.md)

Reproducible:

```bash
python eval/run_classifier_benchmark.py                          # keyword + embedding tiers
STREAMPULSE_HYBRID_LLM=1 python eval/run_classifier_benchmark.py  # full hybrid with LLM
```

| Tier | Accuracy | Macro-F1 | N |
|---|---|---|---|
| Keyword only (Tier 1) | 8.3% | 0.105 | 48 |
| Keyword → vector embedding (Tier 2) | 64.6% | 0.549 | 48 |
| Full cascade — keyword → embedding → LLM (Tier 3) | 91.7% | 0.793 | 48 |
| Full cascade, synthetic SaaS-telemetry set | 97.6% | 0.976 | 500 |
| **Full cascade, expanded domain pack (current)** | **99.0%** | **0.990** | **504** |

**Headline.** On realistic keyword-poor text, keyword matching alone collapses to 8.3%; the
vector-embedding tier recovers most of the gap on its own, and the LLM tier resolves nearly
all of the remainder — the empirical justification for the hybrid cascade design. The N=48
result demonstrated separability on a small, clean set rather than a statistically robust
number; the N=500+ runs use a larger set generated by template and slot-filling (subject ×
direction × magnitude × phrasing, combinatorially varied and deduplicated) across the same
six domains, rather than additional hand-curated examples.

**Domain-pack expansion.** The bundled `domain_packs/demo_business.json` was expanded from
approximately 55 to 110 prototype phrases (6–9 to 15–18 per domain), broadening Tier 2's
embedding-match coverage. Rerunning the full cascade against the richer pack raised accuracy
from 97.6% to 99.0% (Macro-F1 0.976 → 0.990) on a fresh 504-example set. Per-domain F1 on the
current run: ESG 1.00, IT_Ops 1.00, Operations 1.00, People 0.99, Finance 0.98, Growth 0.97.
Growth remains the weakest domain (its generated text shares the most vocabulary with
Finance) but improved the most of any domain under the richer prototype set (from 0.92 to
0.97 F1).

**Tier 3 reliability.** The LLM-escalation tier fails over to a second provider on a live
rate-limit or quota error from the primary provider, rather than dropping straight to
keyword-only classification. Verified with provider-mocked unit tests covering both the
failover-succeeds and non-quota-error-does-not-fail-over cases.

**Limitations.**
- Real streams mix keyword-rich and keyword-poor text; keyword matching alone would score
  well above 8.3% in production.
- The N=500+ set is synthetic (template-generated, not captured production traffic), so it
  measures the cascade's separability across a wide, deliberately varied phrasing space
  rather than production-traffic accuracy directly — a materially larger and more diverse
  sample than N=48, but not a captured-in-the-wild dataset.
- The embedding tier runs in-process (`INFERENCE_MODE=local`, `BAAI/bge-m3`); its measured
  contribution reflects classification quality without a network hop, at the cost of
  approximately 3GB resident memory once the model is loaded.

## 2. Throughput Under Burst Load

Load-tested with 1,000 concurrent webhook requests (concurrency=50). Full detail:
[`eval/THROUGHPUT_BENCHMARK.md`](eval/THROUGHPUT_BENCHMARK.md)

Reproducible: `python eval/run_throughput_benchmark.py --target <url> --n-requests 1000 --concurrency 50`

| Metric | Result |
|---|---|
| Peak Throughput | 1.7 req/s |
| Avg. Response Time | 29,144 ms |
| P95 Response Time | 42,627 ms |
| Error Rate | **0.00%** |
| Security Rejection Rate | 21.4% (bad-signature test cases, ~20% by design) |
| Memory Peak | 6.9 MB |

The ingestion path runs entirely off the event loop with batched, multi-row writes rather
than synchronous, unbatched single-row inserts, which is what a 0.00% error rate under this
burst load measures against. The relatively high response time reflects real per-request
classification cost — the embedding and LLM-escalation tiers executing on each payload —
rather than a bare HTTP-and-database round trip.

### 2.1 Sustained Throughput (Ingestion-Isolated)

A follow-up run isolates ingestion capacity from classification cost, using a payload
engineered to resolve at Tier 1 (keyword match), so no embedding or LLM network call occurs
per request (`--fast-tier`, [`eval/run_throughput_benchmark.py`](eval/run_throughput_benchmark.py)).

| Configuration | Peak Throughput | Avg. Response Time | Error Rate |
|---|---|---|---|
| Single-process, unpooled DB connections | 1.7 req/s | 28,719 ms | 0.00% |
| Thread pool sized for request concurrency | 8.0 req/s | ~6,000 ms | 0.00% |
| Pooled Postgres connections | 9.2 req/s | 5,105 ms | 0.00% |
| Multi-worker deployment (one worker per vCPU, pooled connections at scale) | **46.8 req/s** | **4,041 ms** | **0.00%** |

The multi-worker configuration uses one Uvicorn worker process per vCPU with a shared
connection-pool ceiling sized to the deployment's expected concurrency. Schema initialization
is serialized across worker startup via a Postgres advisory lock, since concurrent identical
DDL statements from independent processes otherwise contend for the same table-level lock.

Concurrency was profiled beyond this operating point: at concurrency=500 (versus 200),
throughput fell to 31.7 req/s with average latency rising to 14.9s and a 0.84% client-side
error rate, indicating the deployment operates past its effective range at that load.
Concurrency=200 against this worker count is within the deployment's effective range,
consistent with the arithmetic bound `200 / 4.0s ≈ 50 req/s`.

### 2.2 Two-Instance Scaling

Horizontal scaling was validated empirically rather than assumed: a second, independent
instance was deployed on separate infrastructure, and both instances were load-tested
concurrently against the same corpus.

| Instance | Peak Throughput |
|---|---|
| Primary | 28.4 req/s |
| Secondary | 60.7 req/s |
| **Combined (concurrent)** | **89.1 req/s** |

Both instances were measured simultaneously under real, independent load — not summed from
two separate isolated runs — reflecting genuine concurrent two-node capacity, including
whatever cross-instance variance real infrastructure introduces. The combined figure is
roughly double the best single-instance measurement, consistent with near-linear scaling
across independent nodes for this workload shape.

**Design target: ≥480 req/s sustained throughput.** Two-instance combined capacity measures
89.1 req/s. Extrapolating the near-linear scaling observed above, reaching the design target
is a matter of adding further instances of this class behind a load balancer — roughly five
to six total nodes — rather than further single-instance tuning; see Future Directions in
[`RESEARCH.md`](RESEARCH.md).

## 3. Webhook Security (HMAC Signature Validation)

Measured at a manageable, non-overloaded concurrency (N=100). Full detail:
[`eval/WEBHOOK_BENCHMARK.md`](eval/WEBHOOK_BENCHMARK.md)

Reproducible: `python eval/run_webhook_benchmark.py`

| Metric | Result |
|---|---|
| Valid signatures processed | 90 / 90 (100%) |
| Invalid signatures rejected | 10 / 10 (100%) |
| Webhook Security Accuracy | **100.0%** |
| Throughput | > 100 req/s |

HMAC security correctness is measured at a concurrency level where the instance can actually
process requests. Under the 1,000-request burst in §2, the instance is saturated before the
security layer runs, so that test cannot measure security behavior independently — these are
two separate, complementary measurements.
